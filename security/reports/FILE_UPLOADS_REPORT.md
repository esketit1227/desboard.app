# FILE_UPLOADS

## Status: MEDIUM (real vulnerability found and fixed; one architectural gap acknowledged, not fixed)

## Findings

Checked all three things CLAUDE.md requires for file uploads against `server/storage.ts` and every upload/serve route in `server.ts`/`server/portal.ts`.

**1. "Rename all uploads to UUIDs server-side" — already satisfied.** Uploaded bytes are never stored under the user-supplied filename at all. `server/storage.ts` keys every stored blob by the file's internal, server-generated id (`contentPath`/`versionPath` use `file.id`, sanitized again defensively to `[a-zA-Z0-9_-]` before touching the filesystem, even though it's already server-generated). The original filename (`file.name`) is only ever used for display and for the `Content-Disposition` header on downloads — never as a storage path. No fix needed here.

**2. "Store on a separate domain, never on the app origin" — a real, acknowledged architectural gap, not fixed this pass.** This app stores uploaded bytes on local disk (`uploads/`, or a mounted volume via `DATA_DIR`) and serves them from its own origin (`/api/files/:id/content`, `/portal/:token/file/:fileId/view`, and both download routes). Migrating to S3/R2/GCS is a real infrastructure change (new credentials, a new `.env` variable, and a rework of `storage.ts`'s read/write/stream functions) — out of proportion for this audit pass to attempt blind, and not done here. Instead, finding 3 below closes the *specific, concrete* consequence this rule exists to prevent (same-origin script execution from uploaded content), via a narrower and more directly verifiable fix. The residual difference — a same-origin storage architecture is still a larger attack surface in general (e.g., any future bug in a route that serves file bytes inherits the app's own origin's trust) — is a legitimate follow-up recommendation, listed below, not something this pass resolves.

**3. Real vulnerability found and fixed: file type was 100% client-claimed with zero server-side validation, and was trusted for both `Content-Type` *and* `Content-Disposition: inline` when serving content back.** `POST /api/files` (`server.ts`) sets `file.mime = mimeType || "application/octet-stream"` directly from `req.body.mimeType` — no magic-byte check, no allowlist, not even a check against the file's own extension. That value then flows unmodified into `streamContentWithRange`/`streamVersionContentWithRange` (`server/storage.ts`), which — before this fix — set `Content-Type: <mime>` and unconditionally `Content-Disposition: inline` for every file, regardless of type.

**Live-verified exploit path, then fixed:** uploaded a file named `innocent.jpg` with `mimeType: "text/html"` and a body containing `<script>alert(document.domain)</script>`. Before the fix, `GET /api/files/:id/content` served it back with `Content-Type: text/html; Content-Disposition: inline` — a browser opening that URL (which is exactly what `FileVaultApp.tsx`/`ProjectFilesPanel.tsx`/`HandoverFileRow.tsx`'s in-app `<iframe src={contentUrl(file)}>` previews, and the portal's own `/file/:fileId/view` route, do automatically) would execute the script **as this app's own origin** — with the viewer's `db_auth` session cookie automatically attached to any same-origin request the script makes (`HttpOnly` blocks *reading* the cookie's value via JS, not the browser from *sending* it — so an injected script could still act with the victim's ambient session: read/exfiltrate their data, or make writes, via ordinary same-origin `fetch()` calls). This is a real stored-XSS-via-content-type-confusion path, and it is **not** blocked by this pass's own `SECURITY_HEADERS` fix — `/api/files/:id/content` inherits the same global CSP, which necessarily allows `'unsafe-inline'` for script-src (required by the portal's own inline scripts, see that report), so a same-origin inline `<script>` in attacker-served content would still execute even with CSP active. Separately confirmed `image/svg+xml` (SVG can also carry `<script>`) hits the same path.

**Fix**: added an explicit allowlist (`INLINE_SAFE_MIME` in `server/storage.ts`) of types that cannot carry active content — the standard web image/video/audio formats plus `application/pdf`. `streamPathWithRange` (the one function both `/api/files/:id/content`, `/api/files/:id/version/:version/download`'s inline sibling, and the portal's `/file/:fileId/view` and version-view routes all funnel through) now checks the claimed MIME against this allowlist: a match still serves `Content-Type: <mime>; Content-Disposition: inline` exactly as before; anything else — regardless of what was claimed at upload, including `text/html`, `image/svg+xml`, or anything not on the list — is forced to `Content-Type: application/octet-stream; Content-Disposition: attachment`, so the browser downloads it instead of rendering it. **One fix, at the single narrow point every inline-serving route already funneled through, closes the vulnerability everywhere it was reachable** (studio previews and the client portal's own file viewer alike).

**Live-verified the fix**, on a scratch database so no real data was touched: the same `text/html`-labeled file now returns `Content-Type: application/octet-stream; Content-Disposition: attachment`; the same test repeated with `image/svg+xml` gets the same safe result; a genuinely legitimate `image/png` upload still returns `Content-Type: image/png; Content-Disposition: inline` exactly as before — no regression to real preview functionality.

**Download routes were already safe and needed no change.** `GET /api/files/:id/download`, the version-download route, and the portal's own download route all already force `Content-Disposition: attachment` unconditionally (verified independently for each) — a browser doesn't auto-render an attachment-disposed response as a page, so this specific content-type-confusion path was never reachable through them. All three also already sanitize the filename (`file.name.replace(/[^a-zA-Z0-9._ -]/g, "_")`) before it reaches the `Content-Disposition` header, closing a separate, smaller header-injection concern that was already handled.

## What's at risk

Before the fix: any authenticated studio user (this app has no client-facing upload feature — files are studio-uploaded only, confirmed by checking every route that calls `writeContent`/`createFile`) could upload a file mislabeled as an executable web content type and get it rendered as a live page under this app's own origin the moment anyone — themselves, a teammate, or a client viewing it via the portal's file viewer — opened its preview, with that script running under the viewer's own ambient session.

## What's already secure

- Storage paths are keyed by server-generated ids, never the uploaded filename — no path-traversal surface via a crafted filename.
- Download routes were never vulnerable to this specific issue and needed no change.
- Filenames are already sanitized before reaching any `Content-Disposition` header.
- The fix is centralized in the one function every inline-serving route shares, rather than needing four separate patches that could drift out of sync.

## Recommendations

1. **Migrate uploaded-content storage to a separate origin** (S3/R2/GCS, or at minimum a separate subdomain with its own cookie jar) per CLAUDE.md's literal rule — this pass's fix closes the specific script-execution consequence, but a same-origin storage architecture remains a larger, standing surface than the ideal. Not attempted here given the infrastructure/credential setup this requires is out of scope for a single audit pass.
2. Consider adding real magic-byte sniffing at upload time (e.g., checking the first few bytes match the claimed type, or independently deriving a type from content rather than trusting `mimeType` at all) as an additional layer — not required for the vulnerability to be closed today (the serve-time allowlist doesn't depend on trusting the claim), but would make the system correct in a second, independent way rather than relying on one gate.
