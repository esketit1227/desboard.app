# XSS

## Status: LOW (fixed)

## Findings

**The React app has zero XSS surface by construction.** Grepped every `.tsx`/`.ts` file for `dangerouslySetInnerHTML` (the one way to bypass JSX's default text-escaping) — no matches anywhere. Every dynamic value rendered in the studio dashboard goes through normal JSX interpolation, which HTML-escapes by default.

**The real risk surface is the hand-built HTML string renderers** (`src/lib/handoverPage.ts`, `src/lib/portalStates.ts`, `src/lib/oauthStates.ts`, `server/email.ts`) — none of these get JSX's automatic escaping, since they assemble raw HTML strings by hand. All four were read and swept exhaustively, not sampled:

- **`handoverPage.ts`** (the client portal — the highest-stakes surface, since a real client visitor's comment `body`/`author` text flows through it): every leaf-level insertion of user-controlled data — comment author/body, file names, handover title/recipient/client name/note, the studio's own branding text — is wrapped in `esc()` (a complete 5-character HTML-entity escaper: `&`, `<`, `>`, `"`, `'`). Data destined for the page's inline `<script>` blocks (comment pins, video pins, client name) goes through a separate, correct mechanism instead — `jsonScript()`, which does `JSON.stringify` plus an explicit `<` → `<` replacement to prevent a literal `</script>` in comment text from closing the tag early (JSON.stringify alone doesn't escape `<`). Non-text contexts are independently validated rather than escaped: `safeColor()` allow-lists branding accent colors to `#hex` or a bare CSS keyword before they reach an inline `<style>` block (blocking CSS-breakout via a malicious accent value), `safeImageUrl()` allow-lists the branding logo URL to `http(s)://`/`data:image/` schemes (blocking `javascript:`), and the `template` value is checked against the fixed `TEMPLATES` list before reaching a `data-template="..."` attribute (already verified under `ACCESS_CONTROL`). The many "fragment" variables in the file (`filesHtml`, `commentsHtml`, `discussionHtml`, etc.) are compositions of already-escaped pieces, not additional raw-insertion points — traced each one back to its leaf source rather than assuming safety from the variable name.
- **`portalStates.ts`** (portal error/password-gate pages) and **`oauthStates.ts`** (OAuth/SSO error page) each define their own complete, correct `esc()` and apply it at every interpolation point, including `oauthErrorPage()`'s `message` parameter — which matters because two call sites (`server/oauth.ts:299`, `server/sso.ts:267`) pass a caught exception's `.message` or a provider-echoed failure reason through it; since the escaping happens *inside* the shared function rather than at each call site, every caller is automatically safe regardless of how attacker-adjacent the message content might be.

**Real gap found and fixed:** `server/email.ts`'s `reminderEmailHtml()` had its own fourth, *incomplete* `esc()` — it escaped `&`/`<`/`>` but not `"`/`'`. This mattered because `params.portalUrl` is interpolated into an `href="${esc(params.portalUrl)}"` attribute, and `portalUrl` is built in `server.ts:893` as `` `${req.protocol}://${req.get("host")}/portal/${handover.token}` `` — `req.get("host")` reads the raw incoming `Host` header, which is client-controllable (Express doesn't validate its format), including by an authenticated studio member crafting a raw request rather than going through their browser (which sets `Host` itself from the URL and doesn't allow script-controlled override). A `"` in a spoofed `Host` header would have broken out of the `href` attribute in the resulting reminder email sent to the studio's own client. Traced every other `req.protocol`/`req.get("host")` usage in the codebase (`server/billing.ts`'s Stripe checkout URLs, `server/oauth.ts`/`server/sso.ts`'s OAuth redirect URIs) — none of the others land in HTML markup this app renders (Stripe's checkout page is hosted by Stripe; the OAuth/SSO ones go into a `Location` redirect header, not HTML, and a mismatched value there just fails the provider's own redirect-URI check rather than injecting anything). Fixed by making `email.ts`'s `esc()` match the other three files' complete implementation.

## What's at risk

Before the fix: a studio member sending a raw (non-browser) request with a crafted `Host` header to the reminder-email endpoint could inject arbitrary markup/links into an email sent from the studio's identity to their own client's inbox. Narrow in practice (requires an authenticated studio member deliberately crafting a raw HTTP request, and that same member already fully controls the email's `note` field content), but a real, fixable gap in a shared escaping utility rather than a one-off — worth closing regardless of how narrow the practical exploitation path is.

## What's already secure

- The entire React studio dashboard has no XSS surface — no `dangerouslySetInnerHTML` anywhere.
- The portal page (the surface a real, untrusted client visitor's own text flows through) was already fully and correctly defended: HTML-entity escaping for markup context, a separate correct mechanism for JSON-in-`<script>` context, and allow-list validation (not escaping) for the CSS-color, URL, and enum contexts, each matched to what that context actually needs.
- Three of the four hand-rolled `esc()` implementations were already complete; the shared, centralized design of `oauthErrorPage()` in particular means every call site benefits from one correct implementation rather than needing to get escaping right individually.

## Recommendations

None outstanding — the one incomplete escaper is fixed. If a fifth hand-built HTML surface is ever added, prefer extracting one shared `esc()` (all four current implementations are byte-for-byte identical once `email.ts`'s fix is applied) into a common module rather than continuing to hand-copy it — not done in this pass since it's a refactor beyond what the audit's scope calls for, not a fix for a live vulnerability.
